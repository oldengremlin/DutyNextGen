# Як розробляти Duty NextGen

Документ описує правила, за якими цей проєкт розвивається. Він
обов'язковий і для людей, і для AI-асистентів (для останніх машинна
версія тих самих вимог лежить у `CLAUDE.md`).

## Головне у трьох пунктах

1. **Мова спілкування — українська.** Повідомлення комітів, коментарі,
   Javadoc, документація. Виняток — текст логів: він англійською.
2. **Кожен коміт зі зміною коду містить також оновлені `pom.xml`
   (версія за SemVer), `CHANGELOG.md` і `README.md`.** Це не
   опційно — детально нижче.
3. **Формат даних не змінюється.** Місячні файли графіка лишаються тим
   самим текстовим форматом; перехід на JSON/YAML/базу даних — лише за
   явним рішенням власника проєкту.

## Середовище

- **JDK 21**, **Maven**, **git** (застосунок викликає його як зовнішній
  процес).
- **UTF-8-локаль обов'язкова.** `LANG=C.UTF-8` або подібне — інакше
  застосунок навмисно не стартує, а тести з кирилицею в git-комітах
  падають. У `pom.xml` для surefire локаль уже задана, але сам застосунок
  запускати треба з правильною.

```sh
mvn test                     # усі тести
mvn -q package               # jar
mvn javadoc:javadoc -Dshow=private   # має бути без жодного попередження
```

## Мова

| Що | Мова |
|---|---|
| Повідомлення комітів | Українська |
| Коментарі в коді, Javadoc | Українська |
| Текст, який бачить користувач у браузері | Українська |
| Вивід CLI (`add-user`) | Українська |
| **Текст логів (`log.info`, `log.warn`, …)** | **Англійська** |
| Повідомлення технічних винятків, що йдуть у лог | Англійська |
| Ідентифікатори: класи, методи, змінні | Англійська, за конвенціями Java |

Мови не змішуються в межах одного повідомлення логу. Якщо в лог треба
потрапити причині українською (наприклад,
`ScheduleGenerationException`) — передавайте сам виняток
(`log.warn("...", e)`), а не `e.getMessage()`: тоді повідомлення логу
лишається англійським, а українська причина йде стектрейсом як дані.

Межа проста: **лог і стектрейс — англійська, інтерфейс — українська.**
`ResponseStatusException`, `DutyExchangeValidationException` і
`ScheduleGenerationException` показуються користувачу як є, тож вони
українською. `UncheckedIOException`, `IllegalStateException`,
`IOException` — діагностика, тож англійською.

## Стиль коду

- Java 21; віртуальні потоки увімкнені (`spring.threads.virtual`).
- **Javadoc — до всіх методів**, не лише публічних. Приватні
  допоміжні методи документуються нарівні з публічним API: саме в них
  зазвичай живуть неочевидні рішення.
- Javadoc пояснює **чому**, а не переказує **що**. Якщо `WHY` очевидний
  з коду й сигнатури — достатньо одного рядка.
- Не додавати абстракцій і обробників помилок без потреби.
- Проміжні змінні — коли результат використовується двічі або вираз
  важкочитабельний. Для ланцюжків внутрішніх методів проєкту їх краще
  уникати; для зовнішніх API та бібліотек вони допустимі заради
  налагодження.
- `mvn javadoc:javadoc -Dshow=private` має проходити без попереджень —
  зокрема, у записів (`record`) документуються всі компоненти.

## Обов'язкове правило при кожному коміті

Кожен коміт зі зміною коду **мусить** містити також:

1. **`pom.xml`** — оновлену версію за [Semantic Versioning](https://semver.org/lang/uk/):

   | Зміна | Версія |
   |---|---|
   | Нова функція | мінорний реліз: `1.17.x` → `1.18.0` |
   | Виправлення чи дрібне покращення | патч: `1.17.0` → `1.17.1` |
   | Зламна зміна | мажорний реліз: `1.x.y` → `2.0.0` |

2. **`CHANGELOG.md`** — новий розділ `## [X.Y.Z] — YYYY-MM-DD` з
   підрозділами `### Додано`, `### Змінено`, `### Виправлено`.

3. **`README.md`** — оновлені розділи, яких стосується зміна, разом із
   діаграмами.

Версію в інтерфейсі оновлювати вручну не треба: футер сторінки графіка
показує `${appVersion}`, який Maven-фільтрація підставляє з `pom.xml`
при збірці.

**Виняток — суто косметичні зміни**, які не чіпають поведінки
(наприклад, ліцензійні заголовки чи форматування): версію не бампаємо.

### Що писати в `CHANGELOG.md`

Не перелік файлів, а **що змінилось для того, хто цим користується, і
чому**. Якщо виправлено баг — варто описати, як він проявлявся: саме ці
записи потім рятують при розборі схожого випадку через рік. Дивіться
наявні записи як зразок.

## Ключові рішення проєкту

Це не рекомендації, а рамки. Змінювати їх — окреме рішення, а не побічний
ефект іншої задачі.

- **Формат даних не змінюється.** Місячні файли графіка — той самий
  текстовий формат (`[ Names ]` / `[ Dates ]` / `[ LastDayN ]`, позначки
  `D`/`W`/`O`/`I`/`S`/`-`), лише в UTF-8. Людинозрозумілість і зручний
  `git diff` — це і є цінність, яку свідомо зберігаємо.
- **Git — внутрішній, непомітний для користувача журнал.** Команда
  ніколи не працює з git заради редагування графіка. Кожне збереження
  застосунок комітить сам, викликаючи `git` як зовнішній процес
  (`ProcessBuilder`), а не бібліотеку (JGit тощо) — заради прозорості й
  простоти аудиту.
- **Без бази даних.** Дані — текстові файли на диску.
- **Без JavaScript-фреймворків.** Сторінки рендеряться на сервері
  (Thymeleaf). Наявний JS — два невеликі файли для зручності
  (підсвітка рядка/стовпця, копіювання в буфер); усе має працювати й без
  них.
- **Секрети поза git-історією графіка.** `config/users.txt` і
  `duty-caldav.conf` не версіюються разом із даними чергувань.

## Тести

- Нова поведінка супроводжується тестом. Виправлений баг —
  регресійним тестом, у Javadoc якого описано **реальний випадок**, а не
  лише технічну умову (дивіться наявні тести як зразок).
- Тести не залежать від зовнішніх сервісів: CalDAV підміняється
  `FakeCalDavServer`, файли створюються в `@TempDir`.
- Тести з git-комітами вимагають UTF-8-локалі (у `pom.xml` вона задана
  для surefire).
- `mvn test` має бути зеленим перед комітом.

## Безпека

Проєкт розгортається за реверс-проксі, який завершує TLS. Тому:

- застосунок **не** надсилає `Strict-Transport-Security` — це справа
  проксі;
- обмеження частоти спроб входу — теж на проксі (`limit_req`,
  `fail2ban`): HTTP Basic не має ні лічильника спроб, ні затримки.

Усередині застосунку правила такі:

- CSRF увімкнено; кожна форма передає токен явно.
- Перевірка прав — не лише приховуванням кнопки в шаблоні, а й у самому
  контролері. Прямий запит в обхід інтерфейсу має відхилятись так само.
- Дані, що йдуть у `users.txt`, перевіряються на роздільник полів і
  переноси рядків.
- Пошкоджений файл даних не має валити застосунок: його пропускають із
  записом у лог. Один битий файл пропозиції обміну колись давав 500 на
  **кожній** сторінці — саме тому це правило тут.

## Коміти

Повідомлення — українською, у форматі:

```
Короткий рядок: що змінилось (до ~72 символів)

Розгорнутий опис: що саме зроблено і, головне, чому. Якщо
виправлено баг — як він проявлявся.
```

Для релізних комітів прийнято починати з версії:
`1.5.0: аудит безпеки й продуктивності`.

Гілки — від `main`; історію в `main` не переписуємо.

## Структура коду

Куди що класти:

| Пакет | Для чого |
|---|---|
| `domain` | Незмінні `record`-и предметної області. Без залежностей — ні на Spring, ні на файли |
| `schedule`, `template`, `exchange` | Формат, сховище й логіка відповідної сутності |
| `git` | Усе, що знає про git як зовнішній процес |
| `caldav` | Синхронізація з календарем |
| `auth` | Автентифікація, ролі, облікові записи |
| `web` | Контролери й допоміжне для шаблонів |
| `config` | Конфігурація застосунку |

Докладніше — розділ «Структура проєкту» в `README.md`.
