# Duty NextGen — інструкції для Claude Code

Веб-застосунок для планування чергувань системних адміністраторів:
графік по місяцях, ротація за шаблоном, обмін чергуваннями, публікація
в CalDAV, повна історія змін. Java 21 + Spring Boot, без бази даних —
дані лежать текстовими файлами. Опис функцій і архітектури —
`README.md`.

Ці інструкції — машинна форма того самого набору вимог, що й
`CONTRIBUTING.md`. **Обидва файли мусять лишатися узгодженими:**
змінюєш правило тут — зміни його і там (і навпаки), у тому самому
коміті.

## Мова спілкування

Завжди відповідати **українською мовою**. **Спілкуємося українською.** Це головна вимога.

- Усі відповіді, пояснення, аналіз і опис процесу виконання — **українською мовою**.
- Повідомлення комітів, коментарі в коді, Javadoc — **українською** (виняток: усталені англомовні технічні терміни, назви класів, методів і властивостей).
- Текст логів — англійською. Не змішувати мови в межах одного повідомлення логу.
- Ідентифікатори в коді (класи, методи, змінні) — англійською, за конвенціями Java.

Межа проста: **лог і стектрейс — англійська, інтерфейс — українська.**

| Що | Мова |
|---|---|
| Повідомлення комітів, коментарі, Javadoc | Українська |
| Текст, який бачить користувач у браузері | Українська |
| Вивід CLI (`add-user`) | Українська |
| Текст логів (`log.info`, `log.warn`, …) | Англійська |
| Повідомлення технічних винятків, що йдуть у лог | Англійська |
| Ідентифікатори в коді | Англійська |

Винятки, які показуються користувачу як є (`ResponseStatusException`,
`DutyExchangeValidationException`, `ScheduleGenerationException`), —
українською. Діагностичні (`UncheckedIOException`,
`IllegalStateException`, `IOException`) — англійською.

Якщо в лог має потрапити причина українською — передавай **сам виняток**
(`log.warn("...", e)`), а не `e.getMessage()`: тоді повідомлення логу
лишається чисто англійським, а українська причина йде стектрейсом як
дані, не як текст повідомлення.

## Середовище

- **JDK 21**, **Maven**, **git** (застосунок викликає його як зовнішній
  процес — без нього не працює ні збереження, ні тести).
- **UTF-8-локаль обов'язкова** (`LANG=C.UTF-8` чи подібна). Імена
  авторів і повідомлення git-комітів ідуть дочірньому процесу через
  `sun.jnu.encoding`, а не `file.encoding` — без UTF-8-локалі кирилиця
  мовчки пошкодиться. Застосунок навмисно не стартує, якщо локаль не та.

```sh
mvn test                              # усі тести
mvn -q package                        # jar
mvn javadoc:javadoc -Dshow=private    # має бути без жодного попередження
```

## Домен та стиль коду

- Java 21 (віртуальні потоки), Maven
- Назви методів і змінних — англійські; коментарі/логи — за потребою
- Не додавати зайвих абстракцій і обробників помилок без потреби
- Не писати коментарі, якщо `WHY` очевидний з коду
- Проміжні змінні вводити лише коли результат використовується двічі або вираз важкочитабельний; для ланцюжків внутрішніх методів проекту — уникати зайвих; для зовнішніх API/бібліотек — допустимі заради налагодження
- **Javadoc — до всіх методів**, не лише публічних: приватні допоміжні
  документуються нарівні з публічним API, бо саме в них зазвичай живуть
  неочевидні рішення. Javadoc пояснює **чому**, а не переказує **що**;
  де `WHY` очевидний із сигнатури — достатньо одного рядка.
- `mvn javadoc:javadoc -Dshow=private` має проходити без попереджень —
  зокрема, у записів (`record`) документуються всі компоненти.

## Тести

Проєкт має набір тестів під `src/test/java`, що фіксує поточну поведінку
майже всього дерева бізнес-логіки.

- **Перед тим, як вважати рефакторинг чи виправлення завершеним —
  прогнати `mvn test`.** Якщо він не проходив автоматично (наприклад,
  чиста правка документації) — можна пропустити, але для будь-якої зміни
  в `src/main/java` це обов'язковий крок, так само як компіляція.
- **Тест впав — спершу зрозумій, ЧОМУ, і лише тоді вирішуй, що
  правити.**
  - Якщо поведінка змінилась **навмисно** (саме це й було метою зміни) —
    онови сам тест під нову поведінку в тому ж коміті. Не видаляй і не
    `@Disabled` тест, щоб змусити збірку пройти без розбору причини.
  - Якщо поведінка змінилась **ненавмисно** (побічний ефект
    рефакторингу) — це регресія, виправляй код, а не тест.
  - Якщо тест був написаний неправильно з самого початку (хибне
    очікування) — виправ тест і залиш короткий коментар `WHY`, якщо
    помилка не очевидна з diff.
- **Нова функціональність чи виправлений баг отримує тест у тому ж
  коміті**, за тим самим принципом, що й `pom.xml`/`CHANGELOG.md`/
  `README.md` (див. «Обов'язкове правило при кожному коміті» нижче) — це
  не окрема майбутня робота.
- У Javadoc регресійного тесту описуй **реальний випадок**, а не лише
  технічну умову: саме ці записи потім рятують при розборі схожого збою
  через рік. Наявні тести — зразок.
- Тести не залежать від зовнішніх сервісів: CalDAV підміняється
  `FakeCalDavServer`, файли створюються в `@TempDir`.

## Обов'язкове правило при кожному коміті

**Кожен коміт із змінами коду повинен містити також:**

1. **`pom.xml`** — оновлену версію відповідно до Semantic Versioning:
   - нова фіча → мінорний реліз (1.17.x → 1.18.0)
   - виправлення / дрібне покращення → патч (1.17.0 → 1.17.1)
   - зламна зміна → мажорний реліз (1.x.y → 2.0.0)

2. **`CHANGELOG.md`** — новий розділ `## [X.Y.Z] — YYYY-MM-DD` з описом усіх змін
   (підрозділи: `### Додано`, `### Змінено`, `### Виправлено`)

3. **`README.md`** — оновлені розділи, що стосуються змінених функцій. Оновлюємо діаграми.

4. **Тест** — на нову поведінку чи на виправлений баг (див. «Тести» вище).

Це не опціонально. Якщо зміна коду є — документація й тести оновлюються
в тому самому коміті.

### Коли версію НЕ бампаємо

**Головне правило: зміни поза `src/` версію не піднімають.** Документація,
`Dockerfile`, `dbuild`, `.gitignore`, CI, будь-що в корені репозиторію —
не реліз, скільки б там не було рядків.

Усередині `src/` версію піднімає лише те, що змінює **зібраний
застосунок**, який бачить користувач:

| Змінилось | Бамп версії |
|---|---|
| `src/main/java` | **Так** |
| `src/main/resources/` — Thymeleaf-шаблони, JS, CSS, `application.yml` | **Так** |
| Будь-що поза `src/` | Ні |
| Лише `src/test/` без зміни `src/main` | Ні |
| Косметика в `src/main`: ліцензійні заголовки, форматування, друкарські помилки в коментарях | Ні |

Логіка проста: версія у футері сторінки — це версія застосунку. Якщо
зібраний застосунок поводиться й виглядає точно так само, версії нема
чого змінюватись.

Якщо зміна документації йде в межах уже відкритої, ще не випущеної
версії — доповнюй її наявний розділ у `CHANGELOG.md`, а не заводь новий.

У `CHANGELOG.md` пиши не перелік файлів, а **що змінилось для того, хто
цим користується, і чому**. Для виправленого бага — як він проявлявся.

## Безпека

Застосунок розгортається за реверс-проксі, який завершує TLS. Тому:

- **не** надсилаємо `Strict-Transport-Security` — це справа проксі;
- обмеження частоти спроб входу — теж на проксі (`limit_req`,
  `fail2ban`): HTTP Basic не має ні лічильника спроб, ні затримки.

Усередині застосунку:

- CSRF увімкнено; кожна форма передає токен явно.
- Перевірка прав — не лише приховуванням кнопки в шаблоні, а й у самому
  контролері. Прямий запит в обхід інтерфейсу має відхилятись так само.
- Дані, що йдуть у `users.txt`, перевіряються на роздільник полів і
  переноси рядків.
- Пошкоджений файл даних не має валити застосунок: його пропускають із
  записом у лог. Один битий файл пропозиції обміну колись давав 500 на
  **кожній** сторінці — звідси це правило.

## Ключові рішення, яких слід дотримуватись

Це не рекомендації, а рамки. Змінювати їх — окреме рішення користувача,
а не побічний ефект іншої задачі.

- **Формат даних не змінюється.** Місячні файли графіка лишаються тим самим
  текстовим форматом (`[ Names ]` / `[ Dates ]` / `[ LastDayN ]`,
  позначки `D`/`W`/`O`/`I`/`S`/`-`), лише в UTF-8 замість KOI8-U. Не
  переходити на JSON/YAML/базу даних без явного запиту користувача —
  саме людинозрозумілість і зручний git-diff цього формату є цінністю,
  яку свідомо зберігаємо.
- **Git — внутрішній, непомітний для користувача журнал.** Команда ніколи
  не працює з git напряму заради редагування графіка. Кожне збереження
  через веб-інтерфейс застосунок комітить сам, викликаючи `git` як
  зовнішній процес (`ProcessBuilder`), а не бібліотеку (JGit тощо) — для
  прозорості й простоти аудиту.
- **Без бази даних.** Дані — текстові файли на диску.
- **Без JavaScript-фреймворків.** Сторінки рендеряться на сервері
  (Thymeleaf). Наявний JS — два невеликі файли для зручності
  (підсвітка рядка/стовпця, копіювання в буфер); усе має працювати й без
  них.
- **Секрети поза git-історією графіка.** `config/users.txt` і
  `duty-caldav.conf` не версіюються разом із даними чергувань.
- **Контейнер працює від `root` — це свідоме рішення, не недогляд.**
  Сервер підконтрольний власнику, контейнер ізольований, і навіть повне
  знищення файлової системи всередині нього не зачепить хост. Ризик
  зводиться до змонтованих каталогів з даними, а від цього рятують
  бекапи, а не непривілейований користувач. Перехід на non-root зламав
  би права наявних томів, тож не робити цього «заодно» з іншою задачею.
- **Проєкт, з якого все починалось (`Duty`) — окремий репозиторій,
  незалежний деплой-цикл.** Нічого тут не посилається на його файли чи
  шляхи; походження історії (одноразовий імпорт з CVS-репозиторію)
  задокументовано в `CHANGELOG.md` і в розділі «Походження» `README.md`,
  а не тут.
- **Версія в інтерфейсі.** Футер сторінки графіка (`schedule.html`) завжди
  показує поточну версію проєкту (`${appVersion}`) — підставляється Maven-
  фільтрацією з `pom.xml` (`app.version: '@project.version@'` у
  `application.yml`, читається `ScheduleController`-ом через
  `@Value("${app.version}")`). Оновлювати вручну не потрібно: досить
  дотримуватись SemVer-бампу `pom.xml` з розділу «Обов'язкове правило при
  кожному коміті» вище — футер підхопить нову версію сам при наступній
  збірці.

## Коміти

```
Короткий рядок: що змінилось (до ~72 символів)

Розгорнутий опис: що саме зроблено і, головне, чому. Якщо
```

## Структура коду

| Пакет | Для чого |
|---|---|
| `domain` | Незмінні `record`-и предметної області. Без залежностей — ні на Spring, ні на файли |
| `schedule`, `template`, `exchange` | Формат, сховище й логіка відповідної сутності |
| `git` | Усе, що знає про git як зовнішній процес |
| `caldav` | Синхронізація з календарем |
| `auth` | Автентифікація, ролі, облікові записи |
| `web` | Контролери й допоміжне для шаблонів |
| `config` | Конфігурація застосунку |

Докладніше — розділ «Структура проєкту» в `README.md`.
